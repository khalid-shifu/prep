

offerings:
	1. high availability
	2. scalability or high performence
	3. disaster recovery - backup and restore


Components:
	1. Node: master node/worker node, server/machine
	2. pod: Abstraction over container, a wrapper over container or containers. provide shared ip,
		network and storage
		
		* each pod gets its own IP adress
		* if crashes, new pod is up, and get new IP adress
	
	3. service: * static / permanent ip address can be assigned to each pod
				* if pod dies, service and ip adress will stay
				* external serivce: make app accessible through browser
				* internal service: for things like database
				* service is also a load balancer, then there is 2 node has the same application,
					it forward request with node's pod is least busy.
				
	
	4. ingress: * service url usually IP adress, ingress provides is human readable url
				* with ingress instead of service, request goes to ingress, then it forwards to
					service
					
	5. configMap: * what problem solves? : if database service change, we gotta change application's properties file, create image,
				and then push, which is tideus. What config map does is, configuration data. cannot put username pass
				
	6. secret: * like config map, but for username, pass, and base64 encoded
	
	7. volumes: * persistant storage, not part of kubernetes cluster,  these is out of k8 cluster
	
	8. deployments: service is also a load balancer, then there is 2 node has the same application, it forward request with node's pod is least
					busy. To create 2nd replica of application pod, we wont create 2nd pod. We will define blue prints of for pods, and declare
					how many replica to run. That blue print is called deployments. Scale up and down. Deployement is another wrapper over pods.
					
	
	9. statefulSet: We cannot replicate db with deployments. Will have data sync issue. This is why we will use statefulset. It will work like deployments
			but makes sure db read and writes are synronized. This is tideus. 
			
			
			
			
    
	#########
	Node process:
	#########
	
	Worker::
	
		* each node has multiple pods on it
		* worker nodes do the actual work
		* 3 proces must be installed on every node, that are used to manage the pods
		
		* processes: [worker node]
			1. container runtime: (docker)
			2. kubelet: schedule pods, and containers, *it has inferface with container runtime and pods. 
			3. KubeProxy: responsible forwarding request from services to pods
	
	
	Master: 
		Master node 4 processes, to control, cluster state and worker nodes
		
		1. Api server: Deploy a new application, interact with api server with client (kubelet, UI, dashbaord). Its cluster gate way. 
				Acts as a gate keeps as a authentication. Create new service, deploy new app, create pods.  Validate request and forward to 
				other process. 
				
		2. Scheduler: After api server valides and it hands it over scheduler. Handles, which worker node the new pod will be scheduled.
			Go through the worker nodes and find least busy node then schdule to execute request.
			
		3. Controller manager: If pod dies, need to detect it dies. Detect state changes like crashing of pods. And tries to recover the cluster 
			state. If that happens request to scheduler to schedule the execution.
			
		4. ectd: key value store. Cluster brain. Every change in cluster, get saved in key value store. With this, schedule knows about recourses.
			with this controller manager knows how pod dies. 
		
		In practice, there can be multiple master nodes.
		
		
	Master process has less work so less resource.

	1. organise resources in namespaces
	2. virtual cluster inside a cluster
	3. multiple namespaces inside a cluster
	4. Defualt namespaces
		4.1 kube-system (system process not for us to use)
		4.2 kubernetes-dashboard (specific to minikube)
		4.3 kube-public (has config name, contains cluster info, kubectl cluster-info)
		4.4 kube-node-lease (holds info of heartbeats of node, each nodes gets its own object)
		4.5 default (create resources in the beginning)
		
    $ kubectl create namespace my-namespace
	
	5. create namespace with config file
	
	
	what is the need for this?
	------------------------------
	6. Group resources in namespace (database get different namespace, monitoring name space and so on)
	
	7. Many teams, same application can have issues. Two teams can have similar named deployment, which will
		override other deployment. So, each team can have a namespace
		
	8. Resource sharing: Staging and development both can share nginx or elastic stack
		
	9. Resource sharing: Blue/green deployment. (blue current production, green next production)
	
	10. Access and resource limits on namespaces: limit resources /assign resources to specific namespaces

	     example: volum, accesible through whole cluster

	1. External service should be internal service, and request first come to

	2. spec:
		rules:
		- host: myapp.come
	      http:                 #this http is not same as url why? this is step 2
			paths:
			- backend
			  serviceName: myapp-internal-service
			  servicePort: 8080
			  
	
    3. internal service vs external. internal service does not have nodePort starts
		from 30000. Instead of type loadBalancer (which is used in external),
		type is defualt type: ClusterIP
		
	4. Host: 
		a. valid domain address
		b. map domain name to Node's IP address, which is the entrypoint
			record/map domain to entry point node's IP address
	
	
	5. Ingress YAML wont be enough! We need ingress controller pod which will have
		routing rules.
		
	6. Ingress controller: evaluate rules, manages redirections, entrypoint to 
		cluster. Many third party implementations
	
	7. k8s Nginx Ingress controller
	
	8. We will need a entiry point: which can be software or hardware solution.
		Or in AWS or Azure or other cloud services it can be their load balancers.
		 
	9. Proxy server: 
		- seperate server
		- public IP address and open ports
		- entry point to cluster
		
		
	Request -> proxy server -> ingress controller -> service
